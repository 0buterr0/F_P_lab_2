# Лабораторна робота №2 — багатопотоковий архіватор Хаффмана

Багатопотоковий додаток на Haskell (GHC, ключ `-threaded`), який стискає множину файлів
в один архів алгоритмом Хаффмана й розпаковує його назад. Окрема команда `bench` вимірює
ефективність алгоритму за часом на багатопроцесорній системі: час, прискорення й ефективність
для 1…N потоків.

## Структура

```
huffman-archiver/
├── huffman-archiver.cabal   -threaded, -O2, RTS: -N -A64m
├── app/Main.hs              розбір командного рядка
└── src/
    ├── Huffman.hs           частоти, дерево, канонічні коди, кодування/декодування блоку
    ├── Parallel.hs          пул потоків (forkIO + MVar), спільна черга завдань
    ├── Archive.hs           формат архіву, паралельне стиснення/розпакування, команди
    └── Bench.hs             вимірювання прискорення, генератор тестових даних
```

Використано лише пакети, що входять до складу GHC (`base`, `bytestring`, `containers`,
`array`, `directory`, `filepath`, `text`), тож нічого додатково завантажувати не треба.

## Алгоритм

1. **Частоти.** Кожен файл ділиться на блоки по 1 МБ, і для кожного блоку рахується, скільки
   разів трапляється кожен байт 0…255.
2. **Код Хаффмана.** Для кожного файлу частоти його блоків сумуються й будується дерево
   Хаффмана: два найлегші вузли раз у раз об'єднуються в черзі з пріоритетом (`Data.Map`).
   З дерева беруться лише довжини кодів, а самі коди призначаються **канонічно**. Тому в архіві
   достатньо зберегти 256 довжин, а дерево зберігати не треба. Довжина коду обмежена 32 бітами:
   якщо дерево виходить глибшим, частоти зменшуються вдвічі й дерево будується заново.
3. **Кодування.** Кожен блок кодується незалежно, біти пишуться в 64-бітний акумулятор і
   скидаються в буфер по байту. Блоки вирівняні по байтах, тому розпаковувати їх теж можна
   паралельно.

## Паралелізм

Модуль `Parallel` реалізує пул із `p` потоків (`forkIO`). Завдання лежать у спільній черзі
(`MVar`), і кожен потік, звільнившись, бере наступне. Так навантаження розподіляється рівномірно,
навіть коли файли мають різний розмір. Результати повертаються в початковому порядку через
окремі `MVar`.

Стиснення має три паралельні етапи:

| Етап | Одиниця роботи | Кількість завдань |
|---|---|---|
| підрахунок частот | блок | усі блоки всіх файлів |
| побудова коду | файл | кількість файлів |
| кодування | блок | усі блоки всіх файлів |

Розпакування паралельне на рівні блоків. Кількість ядер, які використовує RTS, задається
через `setNumCapabilities p`, тож вимір для 1 потоку справді виконується на одному ядрі.

## Формат архіву

```
"HUF1" | кількість файлів (u32)
для кожного файлу:
  довжина імені (u16) | ім'я UTF-8 | розмір (u64)
  довжини кодів: 256 × u8 | кількість блоків (u32)
  для кожного блоку: розмір до (u32), розмір після (u32)
  дані блоків
```

Усі числа записано в порядку little-endian. Під час розпакування імена файлів перевіряються
(`..`, абсолютні шляхи), щоб архів не міг записати файли за межі цільової папки.

## Збірка та запуск

```powershell
cabal build
```

Тестові дані: 8 файлів по 16 МБ тексту з частотами букв англійської мови.
```powershell
cabal run huff -- gen testdata 8 16
```

Вимірювання ефективності (1…N потоків, найкращий час із 3 повторів):
```powershell
cabal run huff -- bench testdata
```

Стиснення, перегляд, розпакування:
```powershell
cabal run huff -- compress test.huf testdata -j 8
cabal run huff -- list test.huf
cabal run huff -- decompress test.huf out -j 8
```

Параметри:
- `-j N`: кількість потоків (у `bench` це максимум);
- `-c КБ`: розмір блоку;
- `-r N`: кількість повторів у `bench`.

Команда `bench` спершу перевіряє, що розпаковані дані збігаються з початковими. Потім вона
виводить таблицю й зберігає її в `bench.csv`:

- **прискорення** S(p) = T(1) / T(p);
- **ефективність** E(p) = S(p) / p.

На процесорах із SMT (наприклад, 6 ядер / 12 потоків) приріст після кількості фізичних ядер
зазвичай помітно менший: логічні потоки одного ядра ділять його обчислювальні блоки.
